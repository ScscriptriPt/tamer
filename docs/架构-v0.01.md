# 驯兽师 · 开发架构（v0.01）

> 这份文档回答一件事：这套东西由哪几层组成，每层负责什么，为什么这么切。
> 产品功能清单见对话记录，这里只讲结构。

## 1. 分层与依赖方向

```
┌─────────────────────────────────────────────┐
│ 交互层  ds-bot Bot「驯兽师」                 │
│   instructions（人设/边界）                  │
│   skill（流程：早推 / 回扣 / 分流）           │
│   消息协议（mode 可扩展）                    │
└──────────────────┬──────────────────────────┘
                   │ MCP（stdio，JSON-RPC）
┌──────────────────▼──────────────────────────┐
│ 工具层  MCP server                          │
│   get_state / plan_day / capture /          │
│   review / commit_breakpoint                │
│   只做参数校验、读写、错误翻译               │
└──────────────────┬──────────────────────────┘
                   │ 纯函数调用
┌──────────────────▼──────────────────────────┐
│ 领域核心  零依赖 TypeScript                  │
│   ├ 规则引擎（R1–R6 及后续）                 │
│   ├ 选择器（从池里抽 2 主线 + 1 支线）        │
│   ├ 进度模型（里程碑 / 位置）                 │
│   ├ 验收分级（L1 两问 / L2 复述 / L3 产出物） │
│   └ 渲染器（协议化消息，按 mode 出变体）       │
└──────────────────┬──────────────────────────┘
                   │ 仓储接口（Storage）
┌──────────────────▼──────────────────────────┐
│ 存储   data/*.json  →  以后换 SQLite          │
└─────────────────────────────────────────────┘
```

**依赖只能向下。** 核心不 import 宿主，不读时钟，不读环境变量，不发网络请求。
唯一的例外是工具层可以调核心，核心不能调工具层。

## 2. 组件职责

| 层 | 负责 | 不负责 |
|---|---|---|
| 交互层 | 说人话、决定什么时候多问一句 | 计算、判断规则、记状态 |
| 工具层 | 参数校验、调用核心、把异常翻译成模型能懂的错 | 业务规则 |
| 领域核心 | 所有确定性判断：排哪三块、算不算例外、够不够 75% | 措辞、语气、追问策略 |
| 存储 | 原子读写、schema 版本 | 任何判断 |

## 3. 三条数据流

**早间推送**
```
定时器 → 工具层 plan_day(today) → 核心选块 → 渲染(mode=normal) → 消息
```

**晚间回扣**
```
定时器 → 工具层 review(today) → 核心选验收档位 → 渲染(question L1/L2/L3)
       → 用户回答 → 工具层 commit_review → 落盘
```

**随手捕获**
```
用户一句话 → 模型判断类型（想法 / 断点 / 状态）
           → 工具层 capture(type, text) → 核心去重与计数 → 落盘
```

第三条是唯一让模型做判断的地方，因为它本来就需要语义。

## 4. 六个关键决策

1. **核心不读时钟。** 所有函数显式接收 `today`。理由：否则系统一天只能测一次，且历史数据无法重放。
2. **规则是纯函数。** 输入 `(pool, history, today)`，输出 `plan`。同样输入必须逐字节同样输出。理由：可回放、可测试、出错能复现。
3. **消息是协议，不是模板字符串。** 渲染器接收 `mode` 与 `stage`，返回结构化消息。理由：虚弱启动、严格验收都是同一个渲染器的不同档位，不能复制三份模板。
4. **存储先进 JSON。** 理由：单人、几十条记录、需要手改和 diff。仓储接口隔离，换 SQLite 时只改一个文件。
5. **模型只有两个位置：语义分流、措辞。** 其余一律代码。理由：这条是产品的立身之本，一旦让模型判断「该不该进守门员」，系统第二天就开始漂。
6. **定时器在系统外。** ds-bot 的 schedule 负责叫醒，核心不认识「八点半」这个概念。

## 5. 进度模型（关键设计，v0.1 实现）

**问题：它怎么知道你推进到哪里？**

答案：**它不知道，除非你留下两样东西之一——勾掉的里程碑，或者一条断点。**

所以进度不存「百分比」，存**位置**：

```json
{
  "id": "microwave",
  "milestones": [
    { "id": "m1", "title": "划范围", "done_when": "一页 4 天路线图", "done": true, "done_at": "2026-10-23" },
    { "id": "m2", "title": "第一二章", "done_when": "能复述", "done": false, "done_at": null },
    { "id": "m3", "title": "第三四章", "done_when": "能复述", "done": false, "done_at": null },
    { "id": "m4", "title": "往年卷一套", "done_when": "70 分以上", "done": false, "done_at": null }
  ]
}
```

- 里程碑**不超过 5 个**。超过 5 个说明项目没想清楚，先拆项目。
- 进度 = `done 数量 / 总数`，离散、可验证，不是感觉。
- 断点记录的是「在哪个里程碑里、走到哪、下一步什么」。
- **没有里程碑的项目视为探索性项目**，不参与进度、不进守门员、不受 75% 规则约束。

三条硬规则：

- 禁止手动输入百分比。
- 进度只由三种事件改变：勾掉里程碑、验收通过、断点推进。
- 连续两次验收没有任何 milestone 变化 → 触发一次「这个项目是不是该缩小」。

## 6. 消息协议（v0.01 留位）

```ts
type MessageMode =
  | "normal"        // 常规日程
  | "weak"          // 虚弱启动：只给一个 90 秒动作
  | "exam_week"     // 考试周：只保留硬约束，砍掉探索
  | "recovery"      // 连续中断后第一天：只要求赢一次
```

渲染器签名固定为 `render(plan, { mode, stage })`。v0.01 只实现 `normal`，其余返回 `normal` 并附一行提示——**先把接口钉死，变体后填**。

验收档位同理：

```ts
type ReviewLevel = "L1" | "L2" | "L3";
// L1 两问：做了吗 / 断在哪
// L2 复述：合上书用三句话讲刚学的东西，模型判断有没有漏
// L3 产出物：检查具体产物（一张卷子、一台机器的笔记）
```

档位由项目类型决定：考试类默认 L2，技能类默认 L3，探索类 L1。

## 7. 例外日：判定结果，不是开关

原设计「用户说一句今天不算」太随意，改成事件驱动的归类：

| 事件 | 来源 | 判定 |
|---|---|---|
| 考试 | 项目 deadline | 自动提议，用户确认 |
| 外出/聚会 | 用户提前报备 | 需提前 ≥1 天 |
| 状态崩 | 连续 2 天完成率 0 | 系统提议 |
| 突发 | 用户当天说 | 需给一句原因 |

规则：

- 例外必须先有**事件**，再有**归类**。
- 每次例外记录 `{ reason, source, approved_at }`。
- **连续 3 天例外**触发一次复盘，而不是无限豁免。
- 例外日不生成计划、不问验收、不补债。

## 8. 演进路线

| 阶段 | 存储 | 接口 | 宿主 |
|---|---|---|---|
| v0.01 | JSON | CLI | 定时器 + 本会话 |
| v0.1 | JSON | MCP | ds-bot Bot |
| v0.2 | JSON | MCP | 同上 + 周报 |
| v1.0 | SQLite | MCP | 同上，多人可用 |

换 SQLite 的触发条件：出现「跨多天聚合查询」或「记录超过 500 条」。在那之前 JSON 都够。

## 9. 测试策略

- 规则全部单测，覆盖 R1–R6 每条的正反例。
- 渲染做**快照测试**：同样的 plan 必须逐字节同样输出。
- 时间相关逻辑注入 `today`，用固定日期测，不依赖真实时间。
- 端到端只测一条：`plan new` → `render` → `review` → 再 `plan new` 是否会换手。
- 不做 UI 测试（没有 UI）。
