# 版本与发布规则

> 版本号是**给别人的承诺**，commit 是**给自己的过程**。这两件事混在一起，就会出现一天发四个版本。

## 三条原则

1. **测试通过 ≠ 可以发布。** 测试只说明代码没坏，不说明有人用过。
2. **一个能力切片 ≠ 一个版本。** 写完一个模块只是"过程"，用户能感知的完整能力才是"发布"。
3. **不能回滚已发布的 tag。** 编号错了就认，在 CHANGELOG 里说清楚，不要把历史改得更好看。

## 版本位

| 位 | 什么时候动 | 例子 |
|---|---|---|
| `X.0.0` | 敢让别人装 | `v1.0.0` |
| `0.X.0` | 一个用户能感知的完整能力落地，且真实用了几天 | `v0.2.0` 守门员 |
| `0.x.Y` | 只给已发出去的版本打补丁 | 线上坏了才动 |

## 打 tag 的门槛

三条同时满足才打，缺一条就只提交：

1. 有新的、**用户看得见**的能力（不是"某个模块写完了"）；
2. **真实用过至少 3 天**，不是测试通过；
3. 接下来一周**不打算改接口**。

## 命名

- **commit**：`类型(范围): 说明`，例如 `fix(core): promote 必须带 --next`
- **规格文件**：`docs/规格-<能力>.md`，跟能力走，不带版本号
- **tag**：`vX.Y.Z`，annotated，message 写一句话说清这一版解锁了什么

## 已发布的例外

`v0.01`、`v0.02`、`v0.03`、`v0.03.1` 是早期编号，产生于本项目还没有发布规则的时候。不回滚、不改写，作为事实保留在历史里。

## 当前状态

> 每日闭环（早推 + 晚回扣 + 断点继承 + 想法分流）连续跑满 7 天，中间不出大问题。

在那之前，只提交，不打 tag。今天到明天可能有七八个 commit，版本号仍然是"未发布"。
