# 规格：断点闭环（v0.02，历史）

> 目标只有一个：**明天的第一块，动作从昨天的断点里长出来。**
> 现在计划器只会挑"哪个项目"，不会说"具体做什么"——因为动作来自静态的 `next_action`，两天后就重复了。

## 1. 数据

`PlanBlock` 的 `breakpoint` 从 `null` 变为可写入：

```json
"breakpoint": {
  "at": "2026-10-23T21:40:00+08:00",
  "did": "把第一章看完了，但导波部分没看懂",
  "stuck": "导波方程的边界条件",
  "next": "从边界条件那节重读，先做课后题 3-2"
}
```

- `did` 必填，`next` 必填，`stuck` 可空。
- 一个块只保留最后一条（可覆盖，断点允许修正）。

## 2. CLI

```
node core/src/cli.ts plan breakpoint --date 2026-10-23 --block 2 \
  --did "..." --stuck "..." --next "..."
```

- `--block` 从 1 开始，越界 → 退出码 1，stderr 说明
- 计划不存在 → 退出码 1
- 例外日 → 退出码 1（例外日没有块）
- 已有 `result` 的计划允许写断点（断点常在验收之后补）
- `--at` 可覆盖时间戳，默认当前 ISO

## 3. 新规则 R7：动作来源

`buildPlan` 解析每个 block 的 action 时，优先级改为：

1. block 级显式覆盖（`--action proj#1=...`）
2. **R7 断点**：该项目在 `date-1` 或 `date-2` 的最近一条 `breakpoint.next`
3. `project.next_action`
4. `project.note`
5. 同项目当天第二块 → `REPEAT_ACTION`

约束：

- 只取**最近一条**断点（先比日期，同日期取块号大的）。
- 只看 `date-1`、`date-2` 两天，更早的断点视为过期，不继承。
- 同一项目今天有两个块时，只有**第一块**用断点动作；第二块仍走 `REPEAT_ACTION`（除非有显式覆盖）。
- `done_when` 不参与 R7，仍按原来的回退链。
- R7 是纯函数，输入 `(pool, date, history)`，不读文件。

## 4. 不改的东西

- 不改渲染格式和行数
- 不改 R1–R6
- 不动 `progress` 字段（临时保留，v0.03 换成 milestones 派生值，别在这版改）

## 5. 测试（≥5 条）

1. 昨天有断点 → 今天同项目第一块 action 等于 `next`
2. 断点被 block 级覆盖 > 断点 > next_action 的优先级正确
3. 两天前的断点也能继承；三天前的不能
4. 无断点时回退到 `next_action`
5. CLI `plan breakpoint` 写入后可被 `plan show` 读回；越界块报错退出 1

## 6. 验收

- `node --test core/test` 全绿
- 造一个 10-22 的计划，给微波写断点，然后 `plan new --date 2026-10-23`，渲染出的第一块动作必须是断点里的 `next`
- 贴出这两条命令的实际输出

## 7. 边界

- 不改 `vendor\`、根目录 md
- 不引入依赖，不 git init
